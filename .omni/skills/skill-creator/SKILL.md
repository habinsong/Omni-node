# Skill Creator

사용자가 대화탭이나 텔레그램에서 새 스킬 생성을 요청하면 응답 본문에 `<omni:skill>` 디렉티브를 직접 출력한다. 미들웨어가 이 블록을 후처리해 `.omni/skills/<name>/SKILL.md` 또는 `~/.omninode/skills/<name>/SKILL.md` 파일로 저장한다.

## 기본 원칙

- 사용자가 요청한 동작만 스킬에 담는다. 없는 기능, 없는 도구, 과장된 역할은 추가하지 않는다.
- 스킬은 몇 줄짜리 메모가 아니라 재사용 가능한 실행 지침이어야 한다.
- `description`은 스킬 호출 판단에 쓰이므로 "무엇을 하는지"와 "언제 써야 하는지"를 한 문장에 구체적으로 쓴다.
- 본문은 스킬이 호출된 뒤 적용할 절차, 출력 형식, 예외 처리, 품질 기준을 담는다.
- 불필요한 배경 설명은 줄이고, 실제 행동 규칙과 예시를 우선한다.
- 모호하면 한 가지만 짧게 되묻고, 답을 받은 뒤 디렉티브를 출력한다.

## 디렉티브 형식

디렉티브는 코드블록으로 감싸지 말고 그대로 출력한다.

<omni:skill name="kebab-case-name" description="무엇을 하며 어떤 요청에서 사용할지 구체적으로 쓴 한 줄 설명" scope="project" overwrite="false">
스킬 본문(markdown)
</omni:skill>

속성 규칙:

- `name`: `^[a-z0-9][a-z0-9-]{0,62}$`. 한글, 공백, 언더스코어는 쓰지 않는다.
- 사용자가 영문 이름을 주지 않으면 요청 의도를 짧은 kebab-case로 의역한다.
- `description`: 한 줄만 쓴다. 큰따옴표 안에 들어가므로 큰따옴표 문자는 피한다.
- `scope`: 사용자가 전역, global, 어디서나, 모든 프로젝트를 명시한 경우만 `global`; 그 외는 `project`.
- `overwrite`: 사용자가 기존 스킬 덮어쓰기에 명시 동의한 경우만 `true`.

## 생성 절차

1. 요청에서 스킬의 목적, 호출 상황, 원하는 말투/출력, 금지 사항을 추출한다.
2. 사용 예시가 부족해도 의도가 명확하면 합리적인 최소 범위로 만든다.
3. 이름은 짧고 호출하기 쉽게 정한다. 예: `casual-empathy`, `eli5-explainer`, `pr-review`.
4. `description`에는 스킬 이름을 몰라도 자동 선택할 수 있을 만큼 구체적인 트리거를 넣는다.
5. 본문에는 아래 구조를 기본으로 넣되, 요청에 맞지 않는 섹션은 줄인다.
6. 최종 응답은 짧은 자연어 한 줄 뒤 바로 `<omni:skill>` 블록을 출력한다.

## SKILL.md 본문 기본 구조

본문은 기본적으로 20줄 안팎으로 작성한다. 너무 단순한 톤 스킬도 8줄 미만으로 끝내지 말고, 실제로 적용 가능한 규칙을 넣는다.

```markdown
# 스킬 제목

## 목표
- 이 스킬이 해결할 일을 한두 문장으로 정의한다.

## 사용 흐름
- 입력에서 확인할 핵심 요소를 적는다.
- 답변 또는 작업을 수행하는 순서를 적는다.
- 필요하면 사용자에게 확인할 조건을 적는다.

## 응답 원칙
- 말투, 깊이, 근거 수준, 사용자와의 상호작용 방식을 적는다.
- 모르는 내용, 위험한 요청, 근거 부족 상황을 어떻게 처리할지 적는다.

## 출력 형식
- 기본 답변 구조를 적는다.
- 표, 목록, 코드, 체크리스트 등 필요한 형식을 명시한다.

## 확인 기준
- 답변 전 스스로 확인할 품질 기준을 적는다.

## 예시
- 사용자 입력 예시와 응답 방향을 짧게 적는다.

## 피해야 할 것
- 과장, 추측, 장황한 설명, 원치 않는 조언 등 금지 사항을 적는다.
```

## 유형별 보강 규칙

- 대화/톤 스킬: 첫 문장 방식, 공감 강도, 조언을 줄 조건, 답변 길이, 피할 표현을 적는다.
- 설명 스킬: 대상 독자, 비유 사용 기준, 단계적 설명 순서, 마지막 확인 질문 여부를 적는다.
- 코드/리뷰 스킬: 읽을 자료, 변경 원칙, 테스트/검증, 파일 언급 방식, 위험 보고 방식을 적는다.
- 검색/리서치 스킬: 우선 출처, 최신성 확인, 인용 방식, 불확실성 표기, 결론 구조를 적는다.
- 문서 작성 스킬: 독자, 톤, 섹션 구조, 길이, 예시, 금지 표현을 적는다.
- 반복 작업 스킬: 입력값, 처리 순서, 완료 기준, 실패 시 되묻는 조건을 적는다.

## 품질 기준

- `description`만 보고도 언제 스킬이 켜져야 하는지 알 수 있어야 한다.
- 본문은 "잘 답한다" 같은 추상 표현보다 구체 행동으로 쓴다.
- 사용자가 한 번 말한 선호를 반복 작업에서 일관되게 적용할 수 있어야 한다.
- 출력 형식과 금지 사항이 있어야 한다.
- 추측이 필요한 부분은 확인 질문 또는 "정보 부족" 처리 규칙을 둔다.
- 사용자 요청보다 넓은 권한이나 기능을 스킬에 넣지 않는다.
- `README.md`, 예시 파일, 추가 폴더는 사용자가 명시 요청하지 않는 한 만들지 않는다.

## 좋은 예시

사용자: "초등학생도 이해하게 설명하는 스킬 만들어줘"

초등학생 설명용 스킬을 추가합니다.

<omni:skill name="eli5-explainer" description="어려운 개념을 초등학생도 이해할 수 있게 쉬운 말, 짧은 비유, 단계별 설명으로 풀어야 할 때 사용한다.">
# ELI5 Explainer

## 목표
- 어려운 개념을 초등학생도 이해할 수 있는 말로 바꿔 설명한다.
- 정확성을 유지하되 전문 용어는 쉬운 표현으로 풀어쓴다.

## 사용 흐름
- 먼저 사용자가 묻는 핵심 개념을 한 문장으로 잡는다.
- 일상에서 볼 수 있는 비유를 하나 고른다.
- 원리를 3~5단계로 나눠 설명한다.
- 마지막에 한 줄 요약을 붙인다.

## 응답 원칙
- 문장은 짧게 쓴다.
- 전문 용어가 꼭 필요하면 바로 뒤에 쉬운 뜻을 붙인다.
- 사용자가 원하지 않으면 수식과 긴 역사 설명은 넣지 않는다.

## 출력 형식
- `한 줄 요약`
- `비유`
- `단계별 설명`
- `기억할 점`

## 확인 기준
- 초등학생이 모를 단어가 남아 있으면 쉬운 말로 바꾼다.
- 설명이 너무 길어지면 핵심 원리만 남긴다.

## 피해야 할 것
- "간단히 말하면"이라고 해놓고 어려운 용어를 이어 쓰지 않는다.
- 정확하지 않은 비유를 억지로 쓰지 않는다.
</omni:skill>

## 나쁜 예시

아래처럼 짧은 메모만 넣지 않는다.

```markdown
- 쉽게 설명한다.
- 예시를 든다.
- 친절하게 답한다.
```
